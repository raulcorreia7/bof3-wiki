An EMI entry of type 1 holds one LZ77 stream that the loader decodes into RAM at the entry's load address. All 65 type-1 entries decode correctly: 12,723,580 stored bytes become 21,753,944 decoded bytes. The decoded data are the character sprite banks. This page covers the stream layout, the frame codec, the rules for writing a stream and the header of the decoded blob. The sprite data inside the blob is not covered.

## Decoding in the game

The game stores large sprite data compressed to save disc space. The loader reads the stream sector by sector and decodes it on the fly. The decoder runs on the scratchpad: `EMI_DecodeStep (exe/slus_004_22@0x80164064)` decodes one 1,024-byte half of a sector at a time.

## Payload layout

The payload is a 6-byte header followed by the control stream.

| Offset | Size | Type  | Meaning                                                   |
| -----: | ---: | ----- | --------------------------------------------------------- |
| `0x00` |    4 | `u32` | decoded size                                              |
| `0x04` |    2 | `u16` | marker `0xFFFF` (65 of 65)                                |
| `0x06` |    - | -     | control stream, ends with a frame that starts with `0xFF` |

The stream fills the payload exactly: the `0xFF` terminator is the last byte before the archive's `0x5F` padding ([EMI container](../emi/#padding)).

## Frame codec

The stream is a series of frames. A frame is either a literal run or a back-reference into the last 2,048 decoded bytes. The first byte of a frame, the control byte, selects the kind.

| Control byte  | Frame                                                                                                                                                                                                                                                      |
| ------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `0x10`-`0x1F` | literal run of `0x20 - (ctrl & 0x1F)` bytes, 1 to 16, copied from the stream. A count of 16 is followed by one extension byte that adds to the count, so runs reach 271                                                                                    |
| `0xFF`        | end of stream                                                                                                                                                                                                                                              |
| other         | back-reference: copy bytes from `distance` bytes back, where `distance = 0x800 - (((ctrl & 0xE0) << 3) \| next_byte)` and `length = (ctrl & 0x0F) + 3`. A low nibble of 15 is followed by one extension byte that adds to the length, so lengths reach 273 |

A back-reference may overlap its own output (`distance < length`). Copy it byte by byte from the start, so earlier output bytes repeat. The 65 entries hold 633,673 literal frames (lengths 1 to 271) and 922,056 back-references (lengths 3 to 273, distances 1 to 2,047).

### Worked decode

A payload that starts `06 00 00 00 FF FF` (decoded size 6) and continues `1E 41 42 E1 FE FF` decodes as follows.

| Bytes      | Frame                                                                                                                        | Output so far       |
| ---------- | ---------------------------------------------------------------------------------------------------------------------------- | ------------------- |
| `1E 41 42` | control `0x1E`: literal run of `0x20 - 0x1E = 2` bytes                                                                       | `41 42`             |
| `E1 FE`    | control `0xE1`: distance `0x800 - (0xE0 << 3 \| 0xFE) = 0x800 - 0x7FE = 2`, length `(0xE1 & 0x0F) + 3 = 4`; overlapping copy | `41 42 41 42 41 42` |
| `FF`       | end of stream                                                                                                                | 6 bytes, as stated  |

### Ambiguous control byte

The control byte `0x10` is ambiguous. A length-3 back-reference whose high distance bits are `0xE0` would also start with `0x10`, and it collides with the 16-byte literal escape. No retail entry uses that back-reference. A writer emits a 16-byte literal as `0x10`, a `0x00` extension byte, then the 16 bytes.

## Writing a stream

A stream written under these rules decodes in the game: use the frame forms above, at most 2,047 bytes of distance, lengths 3 to 273 and literal runs up to 271 bytes, and end with `0xFF`. A run of 1 to 15 literal bytes uses one control byte. A run of 16 to 271 uses `0x10`, one extension byte and the bytes.

The rules that the retail encoder used to choose matches are `[unknown]`. A longest-match, nearest-on-tie search with one byte of lookahead round-trips all 65 entries but reproduces no retail payload byte for byte. Two cases show that the retail choice differs:

- In `BPLD012#7` at decoded offset 93, the retail stream copies 3 bytes from distance 92. A nearest-longest search copies from distance 64.
- In `BRTU467#7` at offset 138, the retail stream defers a 9-byte match to take an 8-byte one at the next byte.

## Decoded blob

The decoded data of every type-1 entry opens with the same fixed-shape header.

| Offset | Size | Type      | Meaning                                                     |
| -----: | ---: | --------- | ----------------------------------------------------------- |
| `0x00` |    4 | `u32`     | `0x0C`, constant in 65 of 65                                |
| `0x04` |    4 | `u32`     | offset of the first large section (`0x1B00C` in `BPLD012`)  |
| `0x08` |    4 | `u32`     | offset of the second large section (`0x3600C` in `BPLD012`) |
| `0x0C` |    4 | `u32`     | offset-table entry count, 16 in 65 of 65                    |
| `0x10` |   64 | `u32[16]` | 16 section offset-table offsets                             |

The blob is `[header][section 1][section 2][trailing region]`. Both section offsets are 4-byte aligned in all 65 entries, but they are not 16-byte aligned and they differ per character. Section 1 starts between `0xE780` and `0x306F4`, and section 2 between `0x21EEC` and `0x51B60`.

The distance from section 1 to section 2 is 110,592 bytes in 41 entries and 63,696 to 198,376 bytes in the others. The trailing region has the same split: 110,592 bytes in the same 41 entries and 11,796 to 198,376 bytes in the others. In those 41 entries every region is a whole number of 4,096-byte pages.

The two large sections are the compressed character-sprite data. The decoded blob goes to the entry's load argument: `EMI_LoaderQueuePayload (exe/slus_004_22@0x80162618)` stores the argument in the sector ring's slot table at `0x801464B8`, and `EMI_LoaderReadSector (exe/slus_004_22@0x80163238)` passes that word to `EMI_DecodeBegin (exe/slus_004_22@0x80164028)` as the output address. The [character bank](../character/#load-arguments) lists the load arguments of the `BPLCHAR` and `PLCHAR` blobs, and the [EMI container](../emi/#character-archives) lists the archive shapes.

## Open questions

- The reader of the 16-entry offset table is not located, so the table's meaning beyond its shape is unproven. Settled by: finding the code that reads the table.
- The content of the two large sections is not decoded ([character bank](../character/)).
- The rule that the retail encoder used to choose matches. Settled by: a model that reproduces a retail payload byte for byte.

## Sources and confidence

- **Confidence:** medium. The stream format decodes all 65 entries, but the encoder's choices and the offset table's use are open.
- **Evidence:** the decoder `EMI_DecodeStep (exe/slus_004_22@0x80164064)`, its output address path through `EMI_LoaderQueuePayload`, `EMI_LoaderReadSector` and `EMI_DecodeBegin`, and a decode of every type-1 entry on the disc, checked for size, markers, terminator position and padding. A re-encoder round-trips all 65 entries.
